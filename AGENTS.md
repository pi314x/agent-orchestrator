# AGENTS.md — Agent Orchestrator (MCP inward + A2A outward)

Instructions for AI coding agents (and humans) working in this repository.
`PLAN.md` is the design source of truth; this file is the rules of the road. Read both before changing code.

## Project snapshot

- Orchestrator that coordinates local agents and independent remote agents.
- Inward interface: MCP `2026-07-28` (stateless core) for hosts like Claude Code/Desktop/IDEs.
- Outward + inward interop: A2A `v1.0` — we call other vendors' agents, and can publish our own agents as an Agent Card for others to call.
- Stack: Node.js 22+, TypeScript (strict, ESM), `@modelcontextprotocol/server` v2, A2A JS SDK, Zod v4, SQLite (better-sqlite3, WAL, FTS5), Vitest, pino.
- Package manager: pnpm.

## Layout

- `src/core/` — business logic. **Must not import the MCP SDK or the A2A SDK.** Fully unit-testable, backend-agnostic. Enforced by ESLint, not just convention.
- `src/services.ts` — builds the long-lived handles (DB, registry, job store, runners, scheduler) once per process. The MCP server factory closes over this; nothing per-request goes in it.
- `src/tools/` — thin MCP adapters, one file per tool group. Validate → call core → shape output. No business logic here.
- `src/a2a/` — the A2A gateway. **Must not import the MCP SDK.** `client.ts` calls remote agents; `server.ts` publishes our Agent Card and serves tasks; `card.ts` and `trust.ts` handle fetch/verify/cache.
- `src/schemas/` — Zod schemas shared by tools and core.
- `src/runners/` — local execution backends implementing `Runner` from `runners/types.ts`. The A2A gateway is *not* a runner — it lives in `src/a2a/`, not `src/runners/`.
- `src/proxy/` — downstream MCP client pool, used only to grant tools to **local** agents.
- `src/db/` — schema, migrations, SQLite/Postgres adapters.
- `tests/` — `unit/`, `integration/`, `live/`. Only `live/` ever calls a real model, and only under `RUN_LIVE_TESTS=1`.

## Stack notes

Verified against the installed SDK — check here before guessing at an API.

- **Packages.** The v2 TypeScript SDK is split: `@modelcontextprotocol/server` (`McpServer`, `createMcpHandler`, `serveStdio` from `/stdio`), `@modelcontextprotocol/node` (`toNodeHandler`, `hostHeaderValidation`, `originValidation`), `@modelcontextprotocol/client` (tests). There is no single `@modelcontextprotocol/sdk` v2.
- **Two protocol eras.** `createMcpHandler` serves *modern* (`2026-07-28`, negotiated via `server/discover`, `_meta` envelope per request) and falls back to *legacy* (`2025-11-25` and earlier, via `initialize`) statelessly from the same factory. Exported `LATEST_PROTOCOL_VERSION` is `2025-11-25` — it names the legacy ceiling, not the modern era, so don't assert on it.
- **Statelessness comes free.** `createMcpHandler` builds a fresh `McpServer` per request via `McpServerFactory`, which is exactly protocol rule 1. Never hoist per-request state into the factory's closure — only long-lived handles (DB, logger, config) belong there.
- **HTTP surface.** MCP is served at `/mcp`; `/health` is a plain JSON probe outside the protocol. Host *and* Origin are validated before the handler sees the request.
- **`structuredContent` needs an index signature.** Type a tool's output shape with a `type` alias, not an `interface` — object-literal aliases get an implicit index signature and stay assignable to `Record<string, unknown>`; interfaces do not.
- **pino.** Import `destination` as a named export (`import { destination, pino } from 'pino'`); it is not typed on the named `pino` export.
- **better-sqlite3** is a native module; it only builds because `pnpm.onlyBuiltDependencies` in `package.json` allows its install script. After a fresh clone run `pnpm rebuild better-sqlite3` if the binding is missing.
- **A2A is optional and gated.** `A2A_ENABLED=false` (the default) removes every tool marked `requiresA2A` from the catalog — the `a2a_*` group, `agent_register`, `agent_publish`. A local-only deployment never sees them, which keeps the tool list small for model tool selection. Mark any new interop tool `requiresA2A: true`.
- **Agents can live in the repo as Markdown.** `ORCH_AGENTS_DIR` (default `agents/`) is scanned at startup: frontmatter sets `name`/`role`/`runner`/`model`/`tools`, the body is the system prompt. The directory is the source of truth — `syncFromFiles` creates, updates and soft-deletes `source='file'` agents, and never touches ones made through `agent_create`.
- **Downstream tools are granted per agent, never globally.** `toolserver_register` adds an MCP server; an agent reaches its tools only through `toolGrants` (`"server"` for all, `"server/tool"` for one). Tools arrive in the agent loop namespaced `server__tool`. Deny-list beats allow-list, and an empty allow-list means everything that server offers.
- **Migrations are append-only, and this has bitten us.** `tool_servers` and `agent_templates` were once added to migration 5 *after* it shipped, so a database already at v5 never received them. Always add a new version. `tests/unit/migrate.test.ts` now guards this by upgrading a v5 database and comparing a staged migration against a fresh one.
- **Testing the Host guard.** Node's `fetch` silently drops a forbidden `host` header — drive `node:http` directly when asserting on host validation.
- **IDs must be monotonic.** `src/ids.ts` uses ulid's `monotonicFactory`, not bare `ulid()`. Ids double as pagination cursors (`WHERE id < ?`), and plain `ulid()` can emit out-of-order ids inside one millisecond, which silently corrupts a page boundary.
- **Await `scheduler.shutdown()` before closing the DB.** An aborted run still writes its outcome on the way out; closing the connection first turns that into an unhandled `The database connection is not open`. Tests use the `closeServices` helper for the same reason.
- **Structured output is enforced by the model, not by us.** A job's `outputSchema` is a JSON Schema, and for a local job it reaches the model as the `finish` tool's required `structured` argument, so tool-input validation constrains the shape. (`runStructured`, which uses `jsonSchemaOutputFormat`, only runs for a job with no toolkit — which the scheduler never produces.) There is no local JSON-Schema validator in the dependency tree — do not add a second validation pass without a reason.
- **`openai-compatible` is the default runner**, via the single `DEFAULT_RUNNER` constant in `src/core/templates.ts` that `ORCH_DEFAULT_RUNNER` and every built-in template both read. `.env.example` spells the same value out separately, so `tests/unit/config.test.ts` asserts the three agree. One adapter covers OpenAI, OpenRouter, Ollama, vLLM and LM Studio — `OPENAI_BASE_URL` is the only thing that differs.
- **The anthropic runner is tested against a real wire, not a mock.** `tests/fixtures/fake-anthropic.ts` serves genuine Messages-API SSE over `node:http`, so the runner's streaming parser, tool loop and usage accounting all execute. Point the SDK at it with `new Anthropic({ baseURL: fake.url })`. It caught two real bugs that mocking the runner would have hidden: streamed commentary being concatenated onto the authoritative `finish` result, and `outputSchema` never reaching the model at all.
- **The URL parser canonicalises IPv4 for us, and nothing else.** `new URL()` turns every IPv4 spelling — decimal, octal, hex, short-form — into dotted-quad, so `src/a2a/trust.ts` matches that one form. IPv6 gets no such help: check the hextets, and remember the parser renders IPv4-mapped addresses in hex (`::ffff:7f00:1`), which no dotted-quad match will ever catch.
- **A2A runs on its own port, and only when enabled.** `src/a2a/http.ts` serves the card at `/.well-known/agent-card.json` and JSON-RPC at `/a2a`, started from `index.ts` only when `A2A_ENABLED=true`. Separate from the MCP surface on purpose: different protocol, different audience, and an operator should be able to expose one without the other. Host-validated exactly like the MCP surface, unless `A2A_AGENT_CARD_URL` says a proxy is in front.
- **Bus events are `{kind, data}`, not flat.** `eventBus.publish({kind:'task', id, status})` throws deep inside the SDK's listener (`event.data.status`), nowhere near the call. Use the typed `AgentExecutionEvent` union and never cast it away — the original code cast to `never` and the shape was wrong for as long as it went unexecuted.
- **`DefaultRequestHandler` takes the Agent Card by value.** Publishing or withdrawing a skill cannot change a handler that already exists, so `createA2AServer` rebuilds the handler when the exposed-skill set changes, keeping one long-lived `InMemoryTaskStore` across rebuilds — task state has to survive, since `SendMessage` and `GetTask` are separate calls.
- **The A2A wire format is protobuf JSON, not the TypeScript shape.** A text part goes over the wire as `{"text": "..."}`, while the TS type is `{content: {$case: 'text', value}}`. Build request payloads with the SDK's own `toJSON` (e.g. `SendMessageRequest.toJSON`) instead of hand-rolling them, in tests especially.
- **Aggregate in SQL, not in JavaScript.** `async` does not make JS parallel: pulling rows back to sum them blocks the event loop whatever the driver does. `BudgetTracker.spend` read every historical job and `JSON.parse`d each one — 775 ms of blocking at 200k rows, three times before every job — and became 109 ms as one `SUM(json_extract(...))`. The synchronous driver is fine; unbounded work in the calling thread is not. Suspect any query whose cost grows with history.
- **Ownership is enforced in the stores, never in tool handlers.** `ToolDeps.principal` comes from `principalFor(ctx.authInfo)` once per serving unit; tools spread `ownerFilter(principal)` into list filters and call `getVisible`/`readVisible` instead of `getOrThrow`/`read`. Putting the check in handlers is how one tool ends up forgetting — the same shape as the `toolGrants` scope gap. A caller asking for another owner's row gets NOT_FOUND, not POLICY_DENIED: existence is information. `''` is the single-owner deployment and means "no OAuth", so nothing changes for a loopback server.
- **`resolveAgentTarget`'s three paths all needed a visibility check, and only one had it.** `agentId` called `getOrThrow`; `skillQuery`'s `findBySkill` had no owner filter at all. Either let `delegate`/`fan_out`/`consensus` reach and run a job on another owner's private agent — its system prompt, its runner, its model, its A2A credentials if it's a remote registration — without that owner ever knowing. Every caller of `resolveAgentTarget` now passes a principal; the three call sites that are not a tool handler (`scheduler.spawnChild`, `workflow-engine.startStep`, the A2A inbound executor) each get the right one for their context: the parent job's/run's owner with `isAdmin: false` for the first two (a sub-agent must never reach further than its own owner could), and full admin visibility for the third (an inbound skill's `agentId` was already an admin's explicit choice via the admin-gated `agent_publish`).
- **Shared agents reuse the single-owner sentinel on purpose.** `owner_id = ''` already meant "no isolation, everyone is one caller" in a no-OAuth deployment. Extending it to mean "explicitly shared by an admin" once OAuth is on is a unification, not two meanings colliding — in single-owner mode there is exactly one caller anyway, so calling every agent shared there changes nothing. `getVisible` allows it for everyone; `getManaged` (used by `agent_update`/`agent_delete`) does not, and a non-admin touching a shared agent gets `POLICY_DENIED` naming that explicitly, not `NOT_FOUND` — the agent's existence is already visible to them via `agent_list`, so pretending otherwise would be a worse answer, not a safer one.
- **`agent_template_save` had no admin gate at all**, despite templates being documented as shared-by-design and already-admin-gated. Any authenticated caller could overwrite a built-in template's instructions for every user in the deployment. Found by checking every tool that touches something documented as "shared" for the gate the documentation claimed already existed — it's worth doing that check explicitly rather than trusting the docs to be true of the code.
- **A fake test harness must derive every value from the same source the caller did, or its checks are checking nothing.** Driving a tool handler directly (bypassing the SDK) means `ctx` and `deps.principal` have to be built from the same fake principal, exactly as `server.ts` derives both from one real token — a test harness with `ctx: {}` next to a hand-built `deps.principal.isAdmin: true` will pass tests it shouldn't, because admin-gated checks read `ctx.http.authInfo.scopes`, not `deps.principal.isAdmin`, directly. It also skips the SDK's own Zod-parsing step, so a schema field's `.default(...)` never applies to a directly-invoked handler — pass the value explicitly in the test rather than relying on the default.
- **A column existing in the schema means nothing until something reads and writes it.** `workflow_runs.owner_id` was added in migration 7 alongside `agents`/`jobs`/`artifacts`, but `WorkflowEngine.start()` never accepted an `ownerId` and never wrote it — so every job a workflow step submitted was owned by `''` regardless of who started the run. In a multi-user deployment this didn't just leave workflows "unisolated" (visible to everyone), it made a workflow's own jobs invisible to the person who started it, since `job_list` filters by the caller's own ownerId. `WorkflowRunRecord.ownerId`, `start({ ownerId })` and `startStep(..., ownerId)` close the job-ownership half; `workflow_get`/`workflow_run_get` now also check visibility (`getVisibleWorkflow`/`getVisibleRun`) — check both halves separately when "isolating" a feature, a schema column proves nothing on its own.
- **Resources need the same ownership scoping as tools, and don't get it for free.** `registerResources` takes a `principal` now, threaded from the same `principalFor(ctx.authInfo)` call as the tools' `ToolDeps.principal` — one derivation per serving unit in `server.ts`. This was found the hard way: scoping the memory *tools* to owners left `orch://memory/{namespace}/{key}` (and every other `orch://` resource) completely open, because resource read callbacks are a separate registration path from tool handlers and nothing connected them to `principal` at all. Any future `orch://` resource over owned data must call `getVisible`/`readVisible`, exactly like a tool.
- **A table-level `UNIQUE` constraint cannot be widened in place.** Adding `owner_id` to `memory` needed `UNIQUE(owner_id, namespace, key)` in place of `UNIQUE(namespace, key)`, and SQLite has no `ALTER TABLE ... DROP CONSTRAINT`. Migration 8 rebuilds the table under a temp name, copying rows with explicit `id` values so rowids survive, then rebuilds `memory_fts` and its triggers against the new table. Preserving rowids is what lets the FTS5 external-content index be rebuilt with a plain `INSERT ... SELECT` instead of a per-row reindex.
- **`src/core/` must not import the MCP SDK, and the linter means it.** `principalFor` lives in `auth.ts` precisely because it speaks `AuthInfo`; `core/principal.ts` stays SDK-free. This rule caught a real violation during the ownership work — do not silence it, move the adapter.
- **Any check-then-write on shared state needs one statement.** Two instances share a database, so `SELECT`-then-`UPDATE` is a race however obvious the guard looks. `JobStore.claim` and `ApprovalStore.resolve` both use `UPDATE ... WHERE <still in the expected state> RETURNING *`; copy that shape rather than reading first. For an approval the losing write would have overwritten a reject with an approve.
- **Claiming a job is atomic, and separate from choosing it.** `nextQueued` carries the priority, capacity and starvation rules; `JobStore.claim` is a single `UPDATE ... WHERE state = 'queued' RETURNING *` that decides whether this process actually got it. Two instances sharing a database both see the same queued row, so the claim is the only thing standing between them — and a loser must get `undefined` and move on, never an exception. The old read-then-write let the loser's rejected transition reach the scheduler's catch block, which marked the *winner's* running job failed.
- **`finishedAt` is set on failure too.** Anywhere you test whether work is *done*, test the state, not the timestamp. `fan_out` reduced over failed items because it checked `finishedAt !== undefined` and got the empty `resultText` of every job that died.
- **Templates resolve own properties only.** `lookup` in `core/templating.ts` uses `Object.hasOwn`, and `stringify` never returns `JSON.stringify`'s `undefined` — otherwise `{{inputs.toString}}`, which passes validation because `inputs` is a legitimate root, renders the literal text "undefined" into a model's prompt.
- **Two kinds of skipped step, and only one propagates.** A workflow step skipped by `when: false` is a branch the author chose, so what depends on it still runs. A step skipped because its dependency died carries `error.code = 'DEPENDENCY_FAILED'`, and that marker is what carries the failure transitively. Without it a step two hops below a failure ran anyway, on whatever its template rendered to — usually the empty string.
- **Guard the grant, not the tool.** `agent_create`/`agent_update` are unprivileged, but attaching `toolGrants` needs `orch:admin` — gating `toolserver_register` alone is half a boundary, since the servers it protects are reachable by granting an agent access to them.
- **The A2A poll loop needs its own deadline.** `job.timeoutSec` is optional, so the scheduler's per-job timer may never exist; `maxPollMs` (15 min default) is what stops a remote task that never terminates from polling forever and holding a concurrency slot.
- **A caller-supplied identifier is a resolution point, not just an endpoint** — the same lesson as `resolveAgentTarget`'s agentId path, found again in workflows: `WorkflowEngine.start()`'s `workflowId` reference called the unchecked `getWorkflowOrThrow`, so `workflow_start({ workflowId })` could run a spec belonging to another owner even though `workflow_get` on that same id was already denied. Fixed by giving `start()` an `isAdmin` input alongside `ownerId` and resolving through `getVisibleWorkflow`. Every method that fetches a caller-named record needs its own check; a check on the sibling "get" tool proves nothing about the "start"/"run"/"use" tool sitting next to it.
- **A name or an idempotency key unique across all owners is a covert cross-tenant channel.** Agent names, workflow spec names, job idempotency keys and workflow-run idempotency keys were all `UNIQUE` globally, not per owner — so once ownership was checked everywhere else, a second user simply couldn't pick a name someone else already had, and worse, an idempotency key collision with another owner's key silently handed back *that owner's* record (the lookup had no owner filter). Fixed by scoping every one of these to `(owner_id, name-or-key)`: a partial unique index for agents/idempotency keys, and — since SQLite cannot widen a table-level `UNIQUE` column constraint in place — a full table rebuild for `workflows.name`. Any uniqueness constraint introduced before multi-tenancy existed needs re-auditing once it does; global uniqueness quietly becomes an oracle or a leak.
- **`control()`'s `principal` is optional on purpose, and that's the one exception to "always check."** Every other workflow-run entry point takes a required principal; `control()` doesn't, because `approvals.ts` calls `control(runId, 'resume')` with none when a review resolves — a reviewer resuming a run they don't own is the entire point of an approval gate, not a bypass of one. Don't "fix" this by making the parameter required; it would break the one legitimately shared queue in the system (see README's Ownership section).
- **Peer-to-peer sharing is a grant table, not a second sentinel.** `resource_grants(resource_type, resource_id, owner_id, grantee_id)` (migration 10, `src/core/grants.ts`) names exactly one grantee per row — separate from the `owner_id === SINGLE_OWNER` admin-wide sentinel, which stays for "shared with everyone." `GrantStore` holds no policy itself; `AgentRegistry.share`/`unshare`/`listShares` gate through the existing `getManaged` (owner or admin only) before touching a grant, and `getVisible`/`list`/`findBySkill` add an `OR id IN (...)`/`hasGrant(...)` check alongside the existing owner and sentinel checks. `MemoryStore` follows the same shape but per namespace, not per key — a grant covers every key in `(ownerId, namespace)`, so `readVisible`/`searchVisible` take an explicit `targetOwnerId` rather than trying to infer one, and `searchVisible` refuses to cross owners at all without both an `ownerId` and a `namespace`, since a grant can't be checked against "every namespace this owner has." Both stores default their `GrantStore` constructor argument to `new GrantStore(db)` so every existing call site (`new AgentRegistry(db)`, `new MemoryStore(db)`) keeps compiling — the store holds no state beyond the shared `db` handle, so two instances are harmless.
- **A tool that forgets to stamp `ownerId` on create is the same bug as forgetting to check it on read, just quieter.** `agent_register`'s `agents.create()` call never set `ownerId`, so every registered remote agent (its `credentialsRef` included) defaulted to `owner_id === ''` — the exact sentinel `getVisible` treats as "shared with everyone." A non-admin registering a remote agent unknowingly made it usable by every other caller, with none of the `denySharedWithoutAdmin` gate that guards the equivalent `agent_create({shared: true})` path, because `agent_register` has no `shared` parameter to gate at all. Grep every `.create(`/`.put(`/`.write(`/`.submit(` call site for a missing `ownerId: deps.principal.ownerId` after any change near ownership — a write-side gap is invisible to every read-side test that only checks visibility of things created *correctly*.
- **Resources are a second registration path, and scoping the tool never scopes the resource.** `orch://workflows/{id}` and `orch://workflow-runs/{id}` still called the unchecked `getWorkflowOrThrow`/`getRun` after `workflow_get`/`workflow_run_get` had already been fixed to use `getVisibleWorkflow`/`getVisibleRun` — the same gap this file already flagged once for memory resources, recurring because a tool fix and a resource fix live in different files with no shared checklist. Any future "add a visibility check" change needs a `grep -rn getOrThrow\|getRun\b src/tools src/resources` pass, not just a fix at the tool call site that happened to prompt the change.
- **A resource that resolves an internal id needs the check at every hop that touches caller input, not just the first one.** `job_wait` took caller-supplied `jobIds` straight into `scheduler.wait`, which resolves them via the unchecked `getOrThrow` and returns full `JobRecord`s (`resultText` included) — every other caller of `wait()` only ever waits on a job it just submitted itself in the same call, so the unchecked lookup was safe everywhere except this one caller-facing entry point. `a2a_task_get`/`a2a_task_cancel`/`a2a_push_config_set` had the identical shape one file over, calling `jobs.getOrThrow(args.jobId)` directly. Proving the fix needs a job with no `remoteTaskId` to *not* be the test fixture — the gateway itself throws `NOT_FOUND` for a job with none, which makes an unfixed and a fixed version indistinguishable unless the test stamps a fake `remote_task_id` first and asserts on `JobStore.getVisible`'s exact message rather than a generic `isError`/`NOT_FOUND` substring.
- **`events_query` had no visibility check of any kind, unscoped.** Unlike jobs/agents/runs, the `events` table carries no `owner_id` column — it is keyed by `jobId`/`agentId`/`runId`, whose ownership lives entirely on those other tables. So a non-admin caller must be required to scope every query to one of those three ids and go through that resource's own `getVisible`/`getVisibleRun` check; an unscoped query has nothing to check against and, left alone, hands back every owner's history. `trace_get` had the narrower version of the same gap — `getRun(args.runId)` instead of `getVisibleRun` — one call away from the fix already sitting right next to it in the same file for the `jobId` branch.
- **`approvals.list({ limit: 100 })` is a global, oldest-first page — never use it to look for one run's decision.** The approval-gate resolution loop in `WorkflowEngine.advanceOnce` used exactly that (`.list({ limit: 100 }).find(a => a.runId === runId && ...)`) to check whether a step's approval had been decided. Once a deployment has ever accumulated more than 100 approval rows *system-wide*, a just-resolved decision for the current run sorts past the oldest-100 window and is invisible to that query — the step hangs in `awaiting_approval` forever, even though a human already decided it. `ApprovalStore.findForStep(runId, stepId)` already existed for exactly this (used two lines below it, in the same file, for the identical purpose of not re-gating an already-decided step) and has no such limit. A paginated `list()` is for a human browsing a UI; anything checking "has *this specific* thing been decided" needs a scoped lookup, not a page of everything.
- **`retry_step` reset the step but not its old approval decision.** `findForStep` returns the *most recent* decision for a (runId, stepId) regardless of status, specifically so a resumed run does not re-gate an already-approved step — but that also means a step rejected once stays rejected forever: `retry_step` cleared `step_runs` (state/job_id/error/output) and nothing else, so the next `advanceOnce` pass found the same old `rejected` record and failed the step again instantly, without ever asking for approval a second time. Fixed with `ApprovalStore.deleteForStep`, called from `control()`'s `retry_step` case right after the step reset — clearing the stale decision is what makes the step gate fresh again, same as a step running for the first time. Any "retry a failed step" feature needs to reset *everything* that fed the failure decision, not just the step's own state.
- **A check-then-insert on a UNIQUE column is the same race the codebase already tells you to avoid — it just hides in a different file.** `MessageBus.createChannel` did `SELECT ... WHERE name = ?` and only `INSERT` when nothing came back; `channels.name` is `UNIQUE`. Two callers whose SELECTs both ran before either INSERT committed (two instances sharing a database, matching this file's own "two instances, one database" testing convention) would both attempt the INSERT, and the loser got a raw `SQLITE_CONSTRAINT_UNIQUE` instead of the channel the winner just created — while `JobStore.claim` and `ApprovalStore.resolve` right next to it in the dependency graph already use the correct one-statement `UPDATE/INSERT ... ON CONFLICT ... RETURNING` shape. Fixed with `INSERT ... ON CONFLICT (name) DO UPDATE SET name = excluded.name` (a no-op update whose only job is to make the statement succeed either way) followed by a plain `SELECT`, mirroring how `MemoryStore.write` already does exactly this. **Proving it needed a different kind of test**: calling the public method twice in a row does not reproduce the bug, on the old code *or* the new one — a single synchronous call's own SELECT always sees whatever the previous call already committed, so the guard hides the race from any single-threaded, sequential reproduction. The only way to actually exercise the fix is to skip the guard and run the bare INSERT statement itself twice for the same name with nothing in between, which is exactly what two genuinely racing callers would each do once their SELECTs had both already missed the row.
- **This file also had zero test coverage before this round.** `MessageBus`/`createChannel`/`listChannels` had no test file at all — the entry point through which every one of the bugs above went unnoticed. A component with no tests is not a component that works; it is a component nobody has checked, which is a different thing that happens to look the same until something forces the question.
- **`artifact_delete` had no ownership check of any kind.** `ArtifactStore.delete(artifactId)` is a bare `DELETE ... WHERE id = ?`, and the tool handler called it directly — any authenticated caller could permanently destroy any other owner's artifact just by knowing (or guessing) its id, worse than every read-side leak found this round because it is destructive and irreversible rather than merely disclosive. Added `deleteVisible` (same shape as `readVisible`, which already existed and was already correctly used by `artifact_get`) and pointed the tool at that instead. A store having a `readVisible` right next to an unchecked `delete` is worth grepping for on its own — visibility was clearly a known concept for this type, just not applied to every mutating method.
- **The agent-side toolkit needs its own ownership checks — a job's own `ownerId` does not protect it for free.** `artifact_get` inside `createAgentToolkit` (the tool a *running agent* calls on itself mid-loop, never exposed over MCP) called `ArtifactStore.read()` instead of `readVisible()`. A submitted job's `instruction`/context can put arbitrary text in front of the model, and the model — not the calling user — is what actually picks the `artifactId` argument at each tool call; nothing stops it from trying an id it saw anywhere (shared workflow context, a bus message, a prior tool result) or simply guessed. Every other handler in that same file (`memory_read`/`memory_write`/`memory_search`, `artifact_put`) already threads `job.ownerId` through correctly — `artifact_get` was the one exception. This is the same "resolves a caller-supplied id via an unchecked getter" shape found everywhere else this session, one layer deeper: the "caller" here is the model itself, inside a tool surface with no test file of its own until this round (`tests/unit/toolkit.test.ts` is new).
- **`recoverInterrupted` never actually did the "queued if idempotent" half PLAN.md §10 documents.** It unconditionally failed every job still `running` at startup with `INTERRUPTED`, whether or not it carried an `idempotencyKey` — a safely-resumable job was lost exactly like one that wasn't, and the one existing test (`fails orphaned running jobs on restart`) happened to only cover the non-idempotent path, so the gap between the doc and the code went unnoticed. Fixed by branching on `idempotencyKey` and, for the resumable case, requeuing with a raw `UPDATE ... WHERE state = 'running'` rather than `transition(id, 'queued')` — the state machine deliberately has no general `running -> queued` edge (a `job_retry` on a job that is genuinely still executing, going through that same edge, would let the scheduler `claim()` and run it a second time while the first attempt is still in flight; this raw update is only safe because it runs once at startup, before the scheduler in *this* process could have claimed anything into memory — every `running` row at that moment is orphaned by construction). **Still not built**: the other half of that same PLAN.md sentence, "in-flight A2A tasks are re-polled by their remote task id before being marked interrupted" — nothing re-polls a remote task on restart at all; a `running` `a2a_remote` job with no `idempotencyKey` is simply marked `INTERRUPTED` like any local one, without ever checking whether the remote task actually finished while this process was down. Documented here rather than silently left as one more assumption to trip over.
- **Recovering a job and starting it are two different things, and only one of them makes noise.** Re-queuing an interrupted job via a raw `UPDATE` does not call `pump()` — nothing in `JobScheduler` runs `pump()` except `submit`/`retry`/a finished run's own `finally`, and `recoverInterrupted()` goes through none of those on purpose (see above). Without something to explicitly kick it, a recovered job would sit `queued` until an unrelated job submission happened to nudge the scheduler awake. Added the one-line public `JobScheduler.start()` (calls the private `pump()`) and call it from `index.ts` right after `recoverInterrupted()`. General lesson: a queue that is only ever driven by its own producers has no way to notice work that appeared any other way — anything that inserts `queued` rows from outside that flow needs to independently trigger the thing that consumes them.
- **Two resource leaks on the A2A outward path, both from never undoing a subscription made in a loop.** `OrchestratorExecutor.cancelled` (the inbound side) added a taskId on cancel but never removed one, so every task ever cancelled stayed in memory for the process's life. `A2AGateway`'s `delay()` (the outward polling loop) added an `'abort'` listener to the job's long-lived signal on every single poll interval and only ever removed it via `{ once: true }` — which self-removes on the listener *firing*, not on the far more common path where the timer just elapses normally. An hours-long poll against a slow remote agent left thousands of dead listeners on one `AbortSignal`. Caught by grepping for every `.add(`/`addEventListener(` in a loop or per-call path and checking each had a matching removal on *every* exit path, not just the "interesting" one (abort) — the boring path (success) is exactly the one that's easy to forget because nothing about it looks like cleanup is needed. Node's `events.getEventListeners(target, type)` works on any `EventTarget`, `AbortSignal` included, which is what makes a leak like this actually assertable in a test instead of just reasoned about.
- **`wrapUntrusted` defanged the closing tag in the body, but not in `source` — and `source` is attacker-controlled too.** For a registered remote agent, `source` is that agent's own self-reported Agent Card `name`, exactly as untrusted as its output; the code only stripped quotes from it (to stop it breaking out of the `source="..."` attribute), never checked it for the literal closing-tag string the way `text` already was. A malicious remote agent could set its card name to `evil</untrusted_remote_output>\nSYSTEM: ...` and have that boundary-ending tag land in the output with no quote needed at all — bypassing the escaping applied to the body by injecting through the sibling parameter instead. Fixed by applying the same `CLOSING_TAG` replacement to `source` before stripping quotes. The lesson generalizes: when a function takes two inputs and only one of them is documented as "untrusted, escape it," check whether the other one actually is too before trusting the comment.
- **A documented behavior with no code path behind it, found by tracing a return value nobody read.** `normalizeTaskResult()` (`src/a2a/mapping.ts`) builds an `artifacts` array from a remote task's file/data parts, and PLAN.md §5.7 documents exactly that: "A2A file/data parts returned by a remote task are normalized into artifacts, same as local job output." But `A2AGateway.run()` computed `normalized` and only ever read `.text` and `.structured` off it — `.artifacts` was computed and silently discarded, so nothing a remote agent returned as a file or data part ever reached the artifact store. `RunnerEvent` had no `'artifact'` variant at all to carry one, because a **local** agent never needs one — its own `artifact_put` toolkit call writes to `ArtifactStore` directly, since it has direct store access and the gateway does not. Fixed by adding `{ type: 'artifact', name, content, mimeType? }` to `RunnerEvent`, handling it in `scheduler.execute()`'s event switch (`this.deps.artifacts.put(...)`, scoped to the job's own `ownerId`/`id` exactly like `artifact_put` already does), and having the gateway yield one such event per entry in `normalized.artifacts`. Two-layer test split matches the two-layer fix: `tests/unit/a2a-gateway.test.ts` proves the gateway *emits* the event; `tests/unit/scheduler.test.ts` proves the scheduler *persists* one, using a bare custom `Runner` rather than the real gateway, since persistence is the scheduler's job, not the runner's.
- **A fallback identity is a shared identity, and `ownerId` is the one value this whole codebase treats as never shared by default.** `createJwtVerifier` fell back to the literal `clientId: 'unknown'` for a token with no `sub` claim — and a `sub`-less token is not an edge case to shrug off: a client-credentials / service-account token, the ordinary shape for machine-to-machine OAuth, legitimately has no end-user subject at all. Every unrelated service authenticating that way would silently share one `ownerId` and see each other's private agents, jobs, memory and artifacts — the exact failure mode every other fix this session exists to prevent, this time from the one place identity is minted rather than checked. Fixed by rejecting the token outright (`verifyAccessToken` throws) instead of inventing a shared owner for it. `auth.ts` had no test file at all before this — `tests/unit/auth.test.ts` spins up a real JWKS endpoint over `node:http` and signs real tokens with `jose`'s `SignJWT`, the same "real wire, not a mock" standard already applied to the Anthropic runner (`fake-anthropic.ts`) — `createJwtVerifier` calls `createRemoteJWKSet` itself, so anything short of an actual HTTP fetch and signature check would never exercise the real verification path at all.
- **A normalization key used for tallying leaked into the answer itself.** `consensus`'s vote strategy groups answers by `text.trim().toLowerCase()` to make trivial formatting differences not read as disagreement, which is correct — but it then reported that same lowercased key as the `verdict`, so a winning answer like "The Sky Is Blue" came back as "the sky is blue": a mangled string nobody actually gave. The existing regression test for this whole tool happened to use an all-lowercase mock answer ("the sky is blue"), so `trim().toLowerCase()` was a no-op and the bug produced a passing test by accident. Fixed by tracking one original-cased answer per normalized key alongside the tally, and reading the verdict from that map instead of the key. Any time a value is normalized only for comparison/grouping, check every place that normalized form is *read back out* — a key and a value are not the same thing even when they happen to look identical in whatever fixture wrote the test.
- **A third registration surface, and the third time this exact gap recurred.** `registerPrompts(server, services)` never received a `principal` at all — `createServerFactory` passes one into `registerTools` and `registerResources` (both derived once via `principalFor(ctx.authInfo)`, per serving unit) but not into prompts, so `cross_vendor_review`'s `services.agents.list({ kind: 'remote' })` had no owner filter to apply even if it wanted one. Any caller invoking that one prompt saw every remote agent registered by every user in the deployment, name and trust level both. Tools, resources, and now prompts: three separate registration paths in this codebase, and each one needed its own principal threaded through by hand — nothing here is inherited automatically, so a fourth surface (if one is ever added) needs the identical treatment checked explicitly, not assumed.
- **`wrapUntrusted` defangs the closing tag.** Remote text carrying `</untrusted_remote_output>` would end the wrapper early and the rest would read as trusted. Any future boundary marker needs the same treatment — an unescaped delimiter is not a boundary.
- **A killed child never fires `close`.** The CLI runner settles on `exit` (plus a 250 ms flush window), because a surviving grandchild holds the stdio pipes open and `close` then never fires — a timed-out job hung forever. It also spawns `detached: true` and signals the whole process group (`process.kill(-pid, …)`), or subprocesses outlive the kill. A null exit code means *killed*, never success.
- **`finish` carries the schema.** For a local job the scheduler always supplies a toolkit, so `runStructured` never runs — the only path to structured output is the `finish` tool, whose `structured` argument *is* the job's `outputSchema` (and is required when one was asked for). Changing `outputSchema` plumbing means changing `toolkit.ts`, not the runner.
- **Scheduling is notification-driven, never polled.** `job_wait` and `drain` resolve off scheduler state-change events; the only timers are the per-job timeout and the wait deadline. Tests gate the mock runner on a promise (`deferred()`) so completion is controlled without any sleep.
- **A test-only `as never`/`as any` cast is a tell, not a convenience.** `hardening.test.ts`'s SQL-injection test called `services.agents.list({ skillQuery: q } as never)` — but `AgentListFilter` has no `skillQuery` field; only `findBySkill` (used by `resolveAgentTarget`) takes one and builds the `LIKE` query these metacharacters could actually threaten. `list()` silently ignores an unrecognized property, so the cast that was needed to get past the resulting type error was exactly the sign something was wrong: the test passed regardless of what `q` was, and had never once exercised the code path it claimed to guard. Fixed by calling `findBySkill(q, admin)` directly. Any test that needs a type-suppressing cast to compile is worth reading twice — the cast is usually hiding a call the type checker was right to reject, not a false positive to silence.
- **A step could read `{{steps.X.output}}` for a step it never declared as a dependency.** `templateVars` builds `steps` from every step in the *run*, not just a step's own `dependsOn`, so the placeholder resolves regardless of whether an edge exists between them — but only a declared dependency is guaranteed to have already finished when this step starts. Two independent steps (no edge between them) can be scheduled in either order or in parallel; if the reader happens to start first, `{{steps.X.output}}` renders as an empty string with no error anywhere, at definition time or at render time — the same "quietly wrong instead of failing loudly" shape as the other silent-empty-output bugs in this file, just triggered by a missing edge instead of a missing check. `validateWorkflow` already validates a template's *root* variables (`assertResolvable`) and a step's `dependsOn` entries separately, but never cross-checked the two: an instruction can reference `steps.foo` while `foo` sits nowhere in that step's own `dependsOn`. Fixed by walking `templateVariables()` for every step's `instruction`/`when` and requiring any `steps.<id>` reference to appear in that same step's `dependsOn` — which, as a side effect, also catches a plain typo'd step id that assertResolvable's root-only check could never see.
- **`CardStore.fetchAndCache` had no URL validation at all — the most severe gap this file has, since neither call site needs `orch:admin`.** `agent_register` and `a2a_card_get` (both `profile: 'standard'`) pass their caller-supplied `cardUrl`/`url` straight through `cardUrlFor` into a real `fetch()`, with no `validateFetchUrl` anywhere in the chain — unlike a webhook push-notification callback (`validateWebhookUrl`) and a card signature's `jku` (`createJwksResolver`), both of which already go through it. Any authenticated caller — no admin scope needed — could point this at an internal service or the cloud metadata endpoint and learn whether it answers (200 vs `REMOTE_UNREACHABLE`), sometimes reading the response back through the tool's own output if it happens to parse as `{name: string, ...}`. Fixed with one `validateFetchUrl(cardUrl)` call before the fetch, mirroring exactly how `createJwksResolver` already validates its own URL. New `tests/unit/card.test.ts` — `CardStore` had no test file of its own before this, same gap as `bus.ts`/`toolkit.ts`/`auth.ts`/`mock.ts` earlier in this file; proved with a spy `fetchImpl` that it is never called for a blocked URL, not just that the call eventually throws.
- **The SSRF/loopback guard caught one IPv4-in-IPv6 embedding and missed another.** `isPrivateIPv6` already special-cased `::ffff:0:0/96` (the IPv4-mapped form, found and fixed earlier), but not `64:ff9b::/96` — the NAT64 well-known prefix, RFC 6052, the exact same "an IPv4 address wearing an IPv6 costume" shape under a different prefix. On any network actually running NAT64 (common on IPv6-only cellular and cloud networks), a request to `[64:ff9b::7f00:1]` is genuinely routed to the embedded `127.0.0.1` — and `[64:ff9b::a9fe:a9fe]` reaches the `169.254.169.254` cloud metadata endpoint the same way. This is the one URL-validation function every attacker-supplied A2A URL passes through (webhook push-notification callbacks, and a card signature's `jku` fetched via `createJwksResolver`), so it's worth grepping for every *other* well-known IPv4-in-IPv6 prefix (6to4's `2002::/16` is the next most-cited one, currently also unchecked, though 6to4 relays are largely dead in practice) whenever this function is touched again — a hand-rolled hextet parser has no `isPrivateIPv4`-style single dotted-quad path to fall back on, so each embedding scheme needs its own explicit case.
- **`getManaged` applied its own "existence is already known, so don't pretend otherwise" reasoning to the admin-shared sentinel but not to a peer grant.** A grantee attempting to `agent_update`/`agent_delete`/`agent_share` a peer-shared (not admin-shared) agent fell through to the generic `NOT_FOUND` branch — even though `agent_share` only ever grants read/use access (per README's own "the owner keeps sole write access"), so refusing the write was already correct, just the wrong diagnostic: a caller who had just read and delegated to the exact same agent got told moments later that it does not exist. Fixed by adding a `grants.hasGrant(...)` branch alongside the existing `SINGLE_OWNER` one, both now `POLICY_DENIED`. Purely a diagnostic-accuracy fix — no access actually changes, since NOT_FOUND already refused the write just as completely.
- **`job_submit`'s `dependsOn` was never checked for visibility — a side channel, not a direct read.** `JobStore.create` stores whatever ids `dependsOn` names with no existence or ownership check, and `releaseBlocked()` (run every scheduler pump) resolves each one the same way: `this.get(depId)`, unchecked. A blocked job's own `job.blocked` event — which the caller can read, since it's tied to *their own* job id — reports the dependency's exact state in its message ("Dependency `<id>` failed, so this job cannot start"), and the dependent auto-releases the instant every dependency reaches `'succeeded'`. So an attacker who merely knows (or guesses) another owner's private job id could submit a throwaway job depending on it and learn that job's existence, its exact state, and the precise timing of every state change — all without ever calling `job_get`, which is the one place ownership *was* checked. Same shape as the rest of this file's "resolves a caller-supplied id via an unchecked getter" bugs, just one level removed: the id here isn't read directly, it's read *through* a side effect (the dependent's own event stream and release timing) that nothing thought to gate. `dependsOn` has exactly one call site in the whole codebase — `job_submit`'s tool handler — so the fix is a single loop calling `jobs.getVisible(depId, principal)` for each id before submission, mirroring `job_wait`'s existing check immediately above it in the same file.
- **`retry_step` reset the step_runs row unconditionally, with no check that the step was actually done.** Calling it on a step whose job was still `running` (a plausible mistake — the wrong `stepId`, or a race against a step that just started) never cancelled that job: the row went straight to `pending` with `job_id = NULL`, so `advance()`'s next pass saw a satisfied, pending step and started a *second* job for it — while the first kept running in the background, still holding a concurrency slot and spending budget, its eventual result silently discarded because nothing pointed at it anymore. `control()`'s own `'cancel'` action already had the right shape right next to it (`if (step.jobId !== undefined && !STEP_TERMINAL.has(step.state)) scheduler.cancel(...)`) — `retry_step` just never applied it. Fixed by looking up the target step first and cancelling any live job before resetting the row, plus a basic existence check for `stepId` (there wasn't one at all before). Regression test needed `scheduler.wait([jobId], 'all', ...)` on the specific original job rather than `drain()`, which would hang forever on the brand-new retry job's own never-resolving test gate — `cancel()` only signals the abort, the state transition to `'cancelled'` happens asynchronously as the runner observes it, same as any other cancellation in this codebase.
- **Every OAuth failure answered 500, never 401 — found only by testing the real wire end to end.** `createJwtVerifier` let whatever it threw (every error `jose`'s `jwtVerify` itself raises — bad signature, expired, wrong issuer or audience, malformed JWT — plus this file's own "no sub claim" check) propagate as a bare `Error`. The MCP SDK's `requireBearerAuth` maps a thrown `OAuthError` to the correct status (401 `invalid_token` with a `WWW-Authenticate` challenge, 403 for insufficient scope) but *any other error type* to a bare 500 `server_error` — undocumented in this codebase, only in the SDK source's own comment on `bearerAuthChallengeResponse`. So every real-world auth failure except a well-formed valid token — an expired token being the most common one by far — answered 500. A client implementing the OAuth challenge-response flow correctly (this project's own `StreamableHTTPClientTransport`, whose `authProvider.onUnauthorized` exists specifically to refresh credentials on a 401) never got the chance to reauthorize; it just saw a server error indistinguishable from an actual outage. Every previous multi-user/ownership test in this codebase drove tool handlers directly with a hand-built `Principal`, which calls `principalFor`/`hasScope` directly and never touches `createJwtVerifier` or the SDK's status-code mapping at all — so this was invisible to the entire existing test suite. Found by building the one test that goes through the real wire end to end: a real JWKS HTTP server, a real signed JWT, a real `startHttpServer` with OAuth configured, a real `StreamableHTTPClientTransport` (`tests/integration/oauth-http.test.ts`, `tests/fixtures/jwks.ts` — the latter extracted from `auth.test.ts`'s own fixture so both share it). Fixed by wrapping every failure path in `createJwtVerifier` as `new OAuthError(OAuthErrorCode.InvalidToken, message)`.
- **`input-required`/`auth-required` aren't terminal, and nothing else recognized them either, so a stuck remote task silently burned the whole poll budget.** `isTerminalTaskState` correctly excludes both (they're not done), but the outbound poll loop in `A2AGateway.run` treated "not terminal" as "still working" and just kept polling — up to `maxPollMs` (15 min default) before reporting a generic `TIMEOUT`, with nothing telling the caller the remote agent was actually waiting on *us* to answer something, not just being slow. There's no code path that can answer such a task (would need a whole "resume with more input" feature, not a bug fix), so the fix is to fail fast and say why the moment either state is observed, rather than silently discovering the same thing 15 minutes later. Also deleted `taskStateToJobState` (`mapping.ts`) while auditing this: exported, documented as mapping A2A states onto the job state machine "so a caller reading job_get cannot tell which backend ran the work," and never called from anywhere — dead code implying a mapping that doesn't actually happen anywhere in the real polling path.
- **The A2A HTTP surface checked Host but never Origin — the other half of the DNS-rebinding/CSRF pair.** `src/http.ts` (MCP) validates both, via the MCP SDK's own guards, specifically because they stop two different things: Host validation stops DNS-rebinding (an attacker domain that later resolves to loopback), Origin validation stops a page at *any* origin from posting directly to the loopback server — a browser's `fetch()` always sends a Host matching the URL it targets regardless of the page's own origin, so Host validation alone lets any site the operator's browser has open submit, read or cancel A2A tasks against `127.0.0.1:A2A_HTTP_PORT`. `src/a2a/http.ts` only had the Host check. Can't fix this by importing the MCP SDK's `originValidation` — `src/a2a` is barred from importing it, same rule that keeps `src/core` SDK-free — so it's hand-rolled inline instead, same shape as the file's own Host check: parse `Origin`, reject a present-and-disallowed value, pass when absent (every real A2A peer is a server, not a browser, and sends no Origin at all).
- **A third abort-listener leak, same shape as the other two.** `MockRunner.run`'s gated wait raced `script.gate` against a promise that rejects on abort — but only the abort path removed its own listener (`{ once: true }` fires on the *event*, not on the race being decided), so a gate that resolved normally, the common case for every test that uses one, left the listener on the job's `AbortSignal` forever. Fixed by capturing the handler and removing it in a `finally` around the race, after replacing the redundant synchronous `if (signal.aborted)` check with `signal.throwIfAborted()` up front. New `tests/unit/mock-runner.test.ts` — `MockRunner` had no test file of its own before this, same gap as `bus.ts`/`toolkit.ts`/`auth.ts` earlier in this file.
- **Running out of `maxSteps` was a silent, empty success in both LLM runners.** `runAgentLoop` (anthropic.ts) and `run` (openai.ts) each loop `for (step = 0; step < maxSteps; ...)`, breaking early only when a turn has no tool calls or `toolkit.finished()` is set. A model that just keeps calling tools every turn — a loop, or a task that genuinely needed more steps than the agent's `limits.maxSteps` allowed — hits neither exit, so the loop ends by falling through, `turnText` holds whatever that final tool-call turn's (usually empty) prose was, and the job reports `succeeded` with that as its result: exactly the failure mode `assertUsable` already exists to catch for a refusal or a length cutoff, just from a third direction nobody had guarded. A workflow's next step, or a `delegate` caller, then treats the empty text as the real answer. There was even an existing test for this ("stops at maxSteps instead of looping forever") — it only asserted the request count, never what the loop produced, so it passed against the bug by construction. Fixed with a `let exhausted = true` flag cleared at both legitimate break points, throwing `RUNNER_FAILED` if the loop falls through with it still `true` — same shape in both runners since the bug was identical in both.
- **Three approval scopes and a whole toolkit tool were documented, and nothing ever created them.** `APPROVAL_SCOPES` has `'job'`, `'unverified_card'` and `'budget'` alongside `'workflow_step'`, and PLAN.md's `approval_list` row and MRTR section described all of them as live — a downstream tool's `requireApprovalFor`, an unverified remote agent card, and an A2A task reaching `input-required` all supposedly showed up there for a human to act on. `approvals.create()` is called from exactly one place in the whole codebase (`workflow-engine.ts`, `scope: 'workflow_step'`); `assertTrusted` either throws or silently passes for an unverified card, no A2A code path ever produces `input-required`, and `request_approval` — listed in PLAN.md as a toolkit tool local sub-agents get — doesn't exist in `toolkit.ts` at all (the one place that comes close, a granted tool with `requireApprovalFor` set, just fails the call immediately: "not available inside a running job yet", per its own comment). Same shape as the `recoverInterrupted` gap: a real feature the docs and a tool's own description promised, with nobody having gone back to either build it or say it wasn't there — an agent trusting the `approval_list` description would poll forever for something that will never appear. Fixed by correcting the description and PLAN.md to say what's actually implemented, not by building the missing human-in-the-loop paths, which is a real feature, not a bug fix.
- **`events_query`'s check on `agentId` proved the wrong thing.** The visibility check confirmed the *agent* was visible, then `events.query(args)` filtered purely by `agent_id` with no owner filter at all — correct for `jobId`/`runId`, which already pin to one caller-checked job/run, but wrong for `agentId`: a shared agent is used by many owners, and every one of their `job.submitted` events (full `instruction` text included) carries that same `agent_id`. A non-admin scoping by a shared agent's id got back every other owner's task instructions, not just their own. A visibility check on the *scoping* id is not the same claim as "every row this scope returns belongs to someone who may see it" — that has to be checked per row (or, cheaper, folded into the query) whenever the scoping id can be shared by more than one owner. Fixed by adding `EventQuery.ownerId`, filtered in SQL as `job_id IS NULL OR job_id IN (SELECT id FROM jobs WHERE owner_id = ?)` (keeps agent-level events like `agent.created`, which carry no `job_id`, visible), and passing `ownerFilter(principal)` into every `events.query` call — a no-op for the already-pinned `jobId`/`runId` cases, the actual fix for `agentId`.

## Hard rules — protocol (MCP)

1. **No session state.** Never store anything keyed by connection or session. All state goes to the DB and is addressed by explicit IDs passed as tool arguments.
2. **Do not use sampling, roots or MCP logging** — deprecated in 2026-07-28. Local sub-agents call provider APIs/CLIs directly; observability goes through the EventLog.
3. **stdout is protocol-only in stdio mode.** Log to stderr via pino.
4. **No tool call may block longer than 60 s.** Long work is task-capable (MCP Tasks extension) when negotiated, otherwise return a handle and let the client use `job_wait`.
5. **Confirmations use MRTR** (`input_required`). Always keep the `approval_*` tool fallback working. A2A's `input-required` task state must surface through this same path.
6. **Tool list order is deterministic**, gated by profile in `src/tools/profiles.ts`.

## Hard rules — interop (A2A)

1. **One shape, two backends.** Local and remote agents/jobs share the same tool-level schema (`Agent`, `Job`). Backend-specific detail (raw A2A task, HTTP binding used, etc.) belongs behind the `a2a_*` debug tools, never leaked into `job_get`/`agent_get`'s common fields.
2. **Verify before trust.** Every remote Agent Card is checked against `A2A_TRUST_MODE` before use. `trustLevel` is always shown wherever a remote agent appears — never hidden, never silently upgraded from `unverified` to `verified`.
3. **Remote output is untrusted input.** Text, structured-data parts, and file parts coming back from a remote agent are treated exactly like downstream MCP tool output: they can never change policy, grants, budgets, or trust levels, and returned code/links are never auto-executed or auto-followed.
4. **Credentials are per-registration.** Each `agent_register` gets its own `credentialsRef`. Never share or reuse a credential across two remote agents. Redact from events/transcripts like any other secret.
5. **Publishing is opt-in.** `agent_publish` only exposes agents/templates explicitly marked `exposed=true`. Never publish the full local roster by default.
6. **Webhooks are validated.** Any push-notification callback URL goes through an allow-list/signature check in `src/a2a/trust.ts` before being registered with a remote agent.

## Tool conventions

- Names: `snake_case`, `<noun>_<verb>` (e.g. `job_submit`, `agent_register`). Exceptions only for the shortcut verbs in PLAN.md (`delegate`, `fan_out`, `consensus`) and the `a2a_*` group, which is `a2a_<noun>_<verb>`.
- Register with `server.registerTool(name, { description, inputSchema, outputSchema, annotations }, handler)`.
- Descriptions: start with a verb, say when to use it **and when not to**, max ~3 sentences, mention related tools by name (e.g. `agent_register` should mention `agent_create` and `delegate`).
- Always set annotations (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) exactly as in the PLAN.md catalog. Anything touching a remote agent gets `openWorldHint: true`.
- Return `structuredContent` matching `outputSchema` plus a short text summary. Never dump huge blobs — return an artifact ID instead.
- Errors: `isError: true` with `{ code, message, hint }`. Codes live in `src/errors.ts` — this includes A2A-originated errors (`REMOTE_REJECTED`, `REMOTE_UNVERIFIED`, `REMOTE_UNREACHABLE`), mapped from A2A's standard error object so callers see one consistent shape regardless of backend.
- Pagination: `cursor` + `limit` (default 20, max 100); response has `nextCursor`.
- Every submit/start tool (including remote task creation) accepts an optional `idempotencyKey`.
- IDs: prefixed ULIDs from `src/ids.ts` only.

## Adding or changing a tool — checklist

1. Update the catalog in `PLAN.md` §5 (purpose, inputs, annotations, profile).
2. Add/extend Zod schemas in `src/schemas/`.
3. Implement logic in `src/core/` (or `src/a2a/` for interop-specific logic) with unit tests.
4. Add the adapter in `src/tools/<group>.ts` and assign a profile.
5. Add an integration test through the in-process MCP client — use the mock runner for local paths and the fixture A2A agent for remote paths.
6. Update the `tools/list` snapshot intentionally (`pnpm test -u`) and mention it in the PR.
7. If the tool touches a remote agent, confirm it degrades sensibly when `A2A_ENABLED=false`.

## Testing rules

- CI never calls real LLM APIs or real third-party A2A agents. Use the `mock` runner and an in-repo fixture A2A agent.
- Every bug fix gets a regression test.
- Scheduler and workflow tests use fake timers — no real sleeps.
- Trust/verification logic (`src/a2a/trust.ts`) needs explicit tests for both `verified-only` and `allow-unverified` modes.
- `tests/live/` is the one exception to the first rule, and it is gated twice: `RUN_LIVE_TESTS=1` **and** a non-empty `ANTHROPIC_API_KEY`, or every test skips. `pnpm test` never reaches a model; `pnpm test:live` runs only `tests/live`. Keep live tests few and cheap — they exist to prove the shapes we send are ones the API accepts, which no fake can prove.

## Security rules

- Never log, return or store secrets in events, transcripts or errors; use the redaction helper.
- Treat all sub-agent output — local or remote — as untrusted data (see interop rule 3 above).
- Enforce depth limits and budgets in `src/core/policy.ts` / `budget.ts`, not only in tool adapters.
- CLI runner may only operate inside configured workspace directories.
- HTTP mode (MCP and A2A) binds `127.0.0.1` by default and validates the Host header.
- **Gate the read side of an admin-only resource, not just its writes.** `toolserver_register`/`toolserver_remove` and attaching `toolGrants` to an agent were all behind `orch:admin`, but `toolserver_list`/`toolserver_tools` were not — any authenticated caller could read out every registered downstream MCP server's full connection details (stdio `command`/`args`/`cwd`, or the HTTP `url`) and its `authRef` credential-name reference, despite having no scope that lets them act on any of it. README §Configuration already documented `toolserver_*` as fully admin-gated; the code just hadn't caught up. Fixed by adding `denyWithoutAdminScope` to both read tools in `src/tools/toolservers.ts`. Same shape as the `getManaged`/NAT64/CardStore fixes earlier in this file: an established boundary applied to some siblings but not an adjacent one — always check whether a resource's *read* tools got the same gate as its *write* tools, not just whether the writes are covered. `tests/unit/scopes.test.ts` had no coverage for this at all before.
- **A table with no owner column still needs a visibility check — through whatever it's reached by.** `approvals` has no `owner_id` (same shape as `events`), so `approval_list`/`approval_resolve` in `src/tools/approvals.ts` had *no* ownership check at all: any authenticated caller could list every owner's pending gates — `summary`, the rendered step `instruction` in `payload`, all of it — and approve or reject them outright, bypassing whatever human sign-off another owner's workflow step was waiting on. `events_query` had already solved this exact shape by scoping through the visible `jobId`/`agentId`/`runId`; approvals never got the same treatment. Fixed with an `isApprovalVisible` helper that resolves an approval's `runId` (all real approvals are `workflow_step`-scoped today) or `jobId` through `getVisibleRun`/`jobs.getVisible`, filtering `approval_list` and gating `approval_resolve` before it touches the row — an approval with neither id is admin-only, since nothing ties it to a checkable caller. `src/tools/approvals.ts` had zero test coverage before this, and `getManaged`/NAT64/CardStore/toolserver_list above are the same lesson repeating: whenever one sibling operation on a resource got a security check, explicitly ask whether every other operation on that same resource got it too.

## Code style

- TypeScript strict, no `any` (use `unknown` + narrowing), no default exports.
- Small pure functions in core; side effects at the edges.
- Prettier + ESLint defaults from repo config. Conventional Commits (`feat(a2a): add agent_register`).
